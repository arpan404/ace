## Finding

Apple provides a public extension API for participating in authorization decisions. That establishes a feasible authorization component, not a complete public API for unattended desktop unlock. The reviewed sources do not identify a supported call that starts the locked session's unlock transaction, makes loginwindow consume a custom approval, and later restores the lock. Those control steps remain unverified. Absence from these sources is not proof no supported route exists.

The product behavior and installed interfaces are recorded in the companion [Codex investigation](macos-codex-locked-use.md). This note focuses on Apple's extension contract; it does not establish OpenAI's internal protocol.

The parent independently collected installed-app and authorization-policy metadata. That evidence is kept in the parent's report; this note does not repeat the inspection or infer a proprietary protocol from symbol imports, comments, bundle names, or policy requirements.

## Public Apple extension contract

Apple describes plug-ins as custom mechanisms for system authorization policies, rather than authentication inside an app. A policy selects mechanisms; the engine loads the plug-in into a dedicated host. Hosts have either an anonymous user identity with UI access or root privileges. GUI/window-server code cannot run in the privileged host. Installation places the bundle in `/Library/Security/SecurityAgentPlugins`; `AuthorizationRightSet` registers a referring policy. Mechanism names have the form `Plugin:Mechanism`, with `,privileged` selecting the privileged host. Apple explicitly warns that `AuthorizationTagsPriv.h` is not public API and may change. [Apple, Extending authorization services with plug-ins](https://developer.apple.com/documentation/security/extending-authorization-services-with-plug-ins).

`AuthorizationRightSet` publicly creates or updates explicit policy entries using an authorization reference. Its existence does not make every built-in rule name, private dictionary key, or replacement of Apple's unlock policy a stable contract. [Apple, AuthorizationRightSet](<https://developer.apple.com/documentation/security/authorizationrightset(_:_:_:_:_:_:)>).

### Mechanism lifecycle

| Stage                                   | Documented behavior                                                                                                                                                                                                                                 | Consequence                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AuthorizationPluginCreate`             | The engine calls the entry point once for initialization. It supplies versioned `AuthorizationCallbacks`; the plug-in returns its reference and versioned `AuthorizationPluginInterface`. The returned interface stays valid until `PluginDestroy`. | This is an engine entry point, not an application call to unlock the Mac. [Apple](https://developer.apple.com/documentation/security/authorizationplugincreate)                                                                                                                                                                                     |
| `MechanismCreate`                       | Receives the plug-in reference, engine handle and policy-selected mechanism ID. Returns an instance reference used for later invoke, deactivate and destroy calls.                                                                                  | Bind work to that mechanism instance and engine, rather than a global approval flag. [Apple](https://developer.apple.com/documentation/security/authorizationplugininterface/mechanismcreate)                                                                                                                                                       |
| `MechanismInvoke`                       | Receives the mechanism instance and performs its authorization operation. Arguments, context and hints can supply information about the authorization.                                                                                              | The engine invokes a mechanism selected by policy. The plug-in does not select which desktop session to unlock through this callback. [Apple](https://developer.apple.com/documentation/security/authorizationplugininterface/mechanisminvoke)                                                                                                      |
| `SetResult`                             | Reports the authorization outcome through the supplied engine callback. Completion may be asynchronous; the engine waits for the result before advancing through the mechanism sequence.                                                            | Returning `errAuthorizationSuccess` from `MechanismInvoke` is not the authorization decision. Unbounded waiting can stall authorization. [Apple](https://developer.apple.com/documentation/security/authorizationcallbacks/setresult)                                                                                                               |
| `MechanismDeactivate` / `DidDeactivate` | On interruption, active processing must stop, including initiated threads or UI processes. The mechanism must then acknowledge through `DidDeactivate`; the engine waits for acknowledgement before resuming.                                       | Cancellation must complete cleanup and acknowledgement. This callback does not mean the desktop has been relocked. [Apple, deactivate](https://developer.apple.com/documentation/security/authorizationplugininterface/mechanismdeactivate), [acknowledge](https://developer.apple.com/documentation/security/authorizationcallbacks/diddeactivate) |
| `MechanismDestroy`                      | Releases resources owned by a mechanism instance.                                                                                                                                                                                                   | End pending work before releasing its callback state. [Apple](https://developer.apple.com/documentation/security/authorizationplugininterface/mechanismdestroy)                                                                                                                                                                                     |
| `PluginDestroy`                         | Announces impending unload and requires plug-in resource cleanup.                                                                                                                                                                                   | Runtime cleanup is distinct from uninstalling a bundle or removing policy references. [Apple](https://developer.apple.com/documentation/security/authorizationplugininterface/plugindestroy)                                                                                                                                                        |

`AuthorizationResult` distinguishes allow, deny, undefined failure without retry for the session, and user cancellation. A mechanism decision must be interpreted within the containing policy. Do not generalize a linear mechanism chain's all-allow behavior to alternative `rule` branches or `k-of-n` configurations. The parent's reported alternate unlock branch needs its own policy analysis. [Apple, AuthorizationResult](https://developer.apple.com/documentation/security/authorizationresult), [SetResult](https://developer.apple.com/documentation/security/authorizationcallbacks/setresult).

`RequestInterrupt` interrupts authorization processing and can cause mechanisms to be invoked again. It is not a documented physical-input takeover or desktop-relock API. [Apple, RequestInterrupt](https://developer.apple.com/documentation/security/authorizationcallbacks/requestinterrupt).

Hints last only for the authorization; context may be preserved and exposed to the client depending on flags. Apple warns against reading hint or context values after `SetResult`, because successful reads can return stale values. Neither storage mechanism authenticates a cooperating daemon by itself. [Apple, GetHintValue](https://developer.apple.com/documentation/security/authorizationcallbacks/gethintvalue), [GetContextValue](https://developer.apple.com/documentation/security/authorizationcallbacks/getcontextvalue).

`SFAuthorizationPluginView` supplies custom UI within Apple's authentication/login dialogs, using the callback table and engine handle. It does not document a secure cover across every display or authority to dismiss the lock screen. [Apple, SFAuthorizationPluginView](https://developer.apple.com/documentation/securityinterface/sfauthorizationpluginview).

## Authorization is distinct from controlling session lock state

`AuthorizationCopyRights` requests rights under a policy. It can preauthorize, extend, or partially authorize a set of rights; interaction flags determine whether UI is allowed. The documented result is granted rights or an authorization error. This does not establish that an arbitrary process requesting `system.login.screensaver` causes loginwindow to unlock its session. [Apple, AuthorizationCopyRights](<https://developer.apple.com/documentation/security/authorizationcopyrights(_:_:_:_:_:)>).

The parent's observed unlock-policy branch supports the conclusion that the installed product participates in that flow. It does not establish which process initiates the real unlock request, how the pending request is bound to the turn and session, or how loginwindow receives completion. A requesting-process requirement for `com.apple.security` is not evidence that a helper authenticates its IPC peer, or that only a trusted turn can obtain approval. Imported audit-token and signing APIs likewise do not prove that verification succeeds or how its result controls authorization.

The public plug-in API is therefore a plausible approval gate within an OS-driven transaction. A supported unlock trigger, reliable relock, secure display cover and input interception are separate unanswered parts. No private unlock/control symbol is recommended here.

## Distribution, update and removal boundaries

Apple's general notarization guidance requires valid signatures on distributed executables, appropriate Developer ID identities, secure timestamps, and Hardened Runtime for app and command-line targets. It says plug-ins inherit host entitlements. These are distribution requirements, not proof of a particular entitlement or library-validation configuration in the authorization host. No plug-in-specific signing exception or entitlement granting unattended unlock was established. Notarization is automated checking, not App Review or endorsement of an unlock design. [Apple, Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

For a direct-distribution installer package, Apple specifies a Developer ID Installer identity, distinct from application code-signing identities. Nested code and signable containers are signed individually, then the outermost container is notarized and its ticket stapled. Apple recommends fresh-install, upgrade, duplicate-copy and different-user testing. These general packaging rules do not define an atomic plug-in/policy upgrade transaction. [Apple, Packaging Mac software for distribution](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

Apple marks `AuthorizationExecuteWithPrivileges` deprecated and directs developers to a `launchd`-launched helper and/or Service Management. The parent's observed import is evidence of a linked interface, not a reason to reproduce that installer strategy. [Apple, AuthorizationExecuteWithPrivileges](https://developer.apple.com/documentation/security/authorizationexecutewithprivileges).

`AuthorizationRightRemove` removes a named explicit right. It does not document deleting a plug-in, removing references in other policies, unloading running code, or clearing staged copies. Removing Apple's whole screen-unlock right would not be an appropriate substitute for removing only an application's additions. [Apple, AuthorizationRightRemove](<https://developer.apple.com/documentation/security/authorizationrightremove(_:_:)>).

Apple DTS has discussed staged copies, but not provided a complete update contract in the reviewed thread. A developer reported old staged code and observed that raising the project version selected the new code; Apple's engineer said that matched their expectation and asked about load location and reboot cleanup. The developer's observations remain third-party observations. The Apple response is limited support evidence, not a documented version-selection or cache-removal guarantee. Do not infer a safe cache-deletion procedure. [Apple DTS, thread 835581](https://developer.apple.com/forums/thread/835581).

## Fail-closed requirements and open questions

These are research conclusions and proposed acceptance criteria, not claims about OpenAI's implementation or guarantees of Apple's API.

- Deny the automatic branch if the helper is unavailable, identity checks fail, the attempt expires, the turn ends, or the session/user cannot be bound. An active agent process alone is insufficient authority. Preserve manual unlock independently; fail-closed automatic authorization must not make ordinary authentication unavailable.
- Bind any permit to one attempt, user/session and trusted turn; consume it once. Explicitly address replay, simultaneous attempts, cancellation, helper restart and stale asynchronous replies. Public hints/context do not define such a protocol.
- Give helper communication bounded deadlines and cancellation. Complete required lifecycle callbacks without granting access merely to avoid a stalled UI. Exact timeout/fallback behavior of the built-in unlock policy remains unverified.
- Display cover and input takeover require their own failure model. Establish coverage before unlock; define behavior for new displays, Spaces, display sleep/wake, cover-process crash, input-monitor failure and loss of the agent connection. A normal window covering the desktop does not itself prove locked-screen protection.
- Prove that teardown restores and verifies the locked state after normal completion and failures. Authorization deactivation/destruction alone cannot serve as that proof. The public trigger and relock APIs, their acknowledgements, and recovery if either fails remain unknown.
- Installation needs an explicitly authorized privileged boundary, narrow policy edits and recovery from interruption. Verify effective loaded version before enabling the feature. Update/removal must reconcile application-owned references with other administrators' policy changes and avoid deleting code while policy still requires it. The reviewed docs provide no complete transaction or rollback protocol.

Questions for Apple DTS or an approved isolated compatibility study:

1. Is there a supported API for asking loginwindow to begin screen unlock for an already logged-in session, independently of human interaction? What client identity and session restrictions apply?
2. Which modifications to `system.login.screensaver`, rule alternatives and mechanism ordering are supported across current macOS versions? Which keys and hints are public contracts?
3. What supported API confirms relock and guarantees physical input cannot reach an exposed desktop during transition? What happens if the covering process crashes?
4. What are the supported staging, version-selection, reload, uninstall and rollback semantics? Is reboot or logout required for any change?
5. What authenticates both directions of helper communication when code executes inside an Apple host? A host signature alone does not identify the particular plug-in or trusted turn.
6. Which administrator prompts, approvals and recovery steps are required for install, enable, update and removal? The exact prompt text, ordering and persistence are unknown from the reviewed documentation.

No unlock-trigger experiment or implementation is justified by this research alone. It establishes the public plug-in lifecycle and distribution boundaries, while leaving the session-control protocol unresolved.
