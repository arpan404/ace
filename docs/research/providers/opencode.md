## TL;DR

**Recommendation.** Make the **HTTP server (`opencode serve`) plus a single `GET /global/event` SSE stream** the primary surface, driven through **`@opencode-ai/sdk/v2`** or our own thin client generated from `/doc`. Run **one long-lived `opencode serve` per machine** (not one per project) and address projects with the `directory` query param or the `x-opencode-directory` header. For history import, use the HTTP list/read routes (`/experimental/session`, `/session/:id/message`, `/session/:id/children`). Reading the SQLite DB directly should only be an emergency fallback. Don't use ACP: it drops subagents and questions. Treat the new `/api/*` "v2" surface as experimental, watch it, and build an adapter seam so it can be swapped in later.

Key facts:

1. **Subagents are first-class child sessions.** The `task` tool calls `sessions.create({ parentID: ctx.sessionID, agent, title: "<desc> (@<agent> subagent)" })` (oc:packages/opencode/src/tool/task.ts:156-174). It then writes `metadata.sessionId` / `parentSessionId` onto the parent's running tool part **before** the child runs (task.ts:185-195). The child is created in the same instance/directory, so its `session.created` (with `info.parentID`), message and part events arrive on the same SSE stream as the parent's. Nesting is capped by `subagent_depth`, which defaults to **1**, meaning children can't spawn grandchildren (task.ts:105-117).
2. **Status is per session, in memory, and only `idle | busy | retry`** (oc:packages/schema/src/session-status-event.ts:9-32). OpenCode never derives a tree status. With a foreground task, the parent stays `busy` while its `task` tool part is `running`. With **background subagents** (`OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`), the parent goes `idle` while children keep running. When a child finishes, OpenCode injects a synthetic prompt into the parent, which makes the parent `busy` again (task.ts:228-256). A parent `idle` is therefore not "done". ace has to derive thread status from the whole subtree.
3. **Two event generations ship side by side.** The legacy/v1 runtime (what `POST /session/:id/message` and `/prompt_async` drive) emits `session.*`, `message.updated`, `message.part.updated` (full part snapshots) and `message.part.delta` (`{field, delta}` text streaming). The new core runtime emits `session.next.*` granular events (text/reasoning/tool-input deltas, `tool.called/progress/success/failed`, `step.started/ended`) and backs the **experimental** `/api/session/*` routes (oc:packages/protocol/src/groups/session.ts:374-378). Both appear in the `Event` OpenAPI union (live).
4. **Human-in-the-loop is HTTP-resolvable from any client.** `permission.asked {id, sessionID, permission, patterns, metadata, always, tool?{messageID,callID}}` is answered by `POST /permission/:id/reply {reply: once|always|reject, message?}`. `question.asked {id, sessionID, questions[], tool?}` is answered by `POST /question/:id/reply {answers: string[][]}` or `/reject` (oc:packages/schema/src/v1/permission.ts:26-67, v1/question.ts:18-74). Pending requests exist **only in the serving process's memory**. They are rejected when the instance is disposed (oc:packages/opencode/src/permission/index.ts:46-63).
5. **The default permission policy is permissive.** The built-in default is `"*": "allow"`, with `ask` only for `doom_loop`, `external_directory`, and `*.env` reads (oc:packages/opencode/src/agent/agent.ts:119-135). Unless ace sets session or agent permissions, users will see few approvals.
6. **Liveness:** both SSE endpoints send `server.connected` first and then `server.heartbeat` every **10 s** (oc:packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts:63-71, global.ts:35-42; live). Neither stream offers replay. Only the experimental `/api/session/:id/event?after=<seq>` stream is durable and resumable.
7. **One server can serve many directories.** Instances load lazily per request from `?directory=` / `x-opencode-directory` (default `process.cwd()`). Session-addressed routes auto-route to the session's stored directory (oc:packages/opencode/src/server/routes/instance/httpapi/middleware/workspace-routing.ts:87, 182). `/global/event` carries `{directory, project, workspace, payload}` for **all** instances (oc:packages/opencode/src/event-v2-bridge.ts:34-61).
8. **Churn is high.** About 2 patch releases a week (v1.18.30→34 between 09-09 and 09-30; GitHub releases). The legacy root SDK export `@opencode-ai/sdk` is a frozen, stale generation (no `permission.asked`, `question.*`, `message.part.delta`). Only `@opencode-ai/sdk/v2` is regenerated (oc:packages/sdk/js/script/build.ts:14-70). A package that will replace it, `@opencode-ai/sdk-next`, is already announced (oc:CONTEXT.md:161).

**One server per machine vs. per project.** `opencode serve` starts with no ambient instance (`instance: false`, oc:packages/opencode/src/cli/cmd/serve.ts:7-12). Each request picks its instance from `?directory` / `x-opencode-directory` (falling back to `process.cwd()`). Routes that take a session ID resolve the directory from the session itself (workspace-routing.ts:160-185). One global server works. Per-directory state (status map, pending permissions and questions, LSP, MCP) lives in `InstanceState`, keyed by directory. So `GET /session/status`, `/permission` and `/question` must be called **per directory**.

## 2. Launch, auth, process model

- **Spawn:** `opencode serve --hostname 127.0.0.1 --port 0`. Port `0` tries 4096 first and then any free port (oc:packages/opencode/src/server/server.ts:117-122). The docs claim the default is `4096` (docs/server), which is drift. Parse the stdout line `opencode server listening on http://host:port` (serve.ts:19), or pass an explicit free port. `--cors`, `--mdns` and `--mdns-domain` are also available (`opencode serve --help`, live).
- **Auth:** HTTP Basic, only if `OPENCODE_SERVER_PASSWORD` is set. Username defaults to `opencode` (`OPENCODE_SERVER_USERNAME`) (oc:packages/opencode/src/server/auth.ts:15-33). Without it, serve prints `Warning: OPENCODE_SERVER_PASSWORD is not set; server is unsecured.` (live). For EventSource clients, the middleware also accepts `?auth_token=<base64 user:pass>` (oc:packages/opencode/src/server/routes/instance/httpapi/middleware/authorization.ts:12, 76-80). **ace should always set a random password**, since anything on localhost can otherwise drive the agent.
- **Config injection:** `OPENCODE_CONFIG_CONTENT` (JSON) is how the SDK passes config (server.ts:37-41 in sdk v2). `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_DISABLE_PROJECT_CONFIG` and `OPENCODE_PERMISSION` also exist (oc:packages/core/src/flag/flag.ts). Runtime flags: `OPENCODE_CLIENT` (default `"cli"`; it gates the `question` tool to `app|cli|desktop` unless `OPENCODE_ENABLE_QUESTION_TOOL`), `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`, `OPENCODE_EXPERIMENTAL_PLAN_MODE`, `OPENCODE_EXPERIMENTAL_EVENT_SYSTEM`, and others (oc:packages/opencode/src/effect/runtime-flags.ts:16-57; registry.ts:207). **Don't set `OPENCODE_CLIENT` to anything outside `app|cli|desktop`, or the question tool disappears.**
- **Providers/models:** `GET /provider` (`all`, `default`, `connected`), `GET /config/providers`, `PUT/DELETE /auth/:providerID`, `/provider/:id/oauth/{authorize,callback}` (live spec; docs/server). Credentials are stored in `~/.local/share/opencode/auth.json` (local listing). Model is chosen per prompt via `model:{providerID, modelID}` plus `variant` (oc:packages/opencode/src/session/prompt.ts:1499-1520).
- **Worktrees/multi-dir:** `/experimental/worktree` CRUD, and `/experimental/workspace*` behind `OPENCODE_EXPERIMENTAL_WORKSPACES` (live spec). A session stores `directory`, `projectID`, `workspaceID?` (oc:packages/schema/src/v1/session.ts:543-571).
- **Version gating:** `GET /global/health` → `{"healthy":true,"version":"1.18.33"}` (live). Each session also records the `version` that created it (v1/session.ts:558). Gate on a semver range, and feature-probe `/doc` for operation IDs (for example `permission.reply`, `question.reply`) rather than trusting versions alone. `GET /experimental/capabilities` → `{backgroundSubagents}` (oc:packages/opencode/src/server/routes/instance/httpapi/handlers/experimental.ts:40).
- **Process ownership caveat:** the TUI (`opencode`) runs its **own** server in its own process (docs/server: "If you have the opencode TUI running, `opencode serve` will start a new server"). Every process shares the SQLite DB, but status, pending permissions and questions, the runner registry and the event bus are in-process. A session driven by the user's TUI shows **no live events** on ace's server [inferred from code: status.ts uses `InstanceState` maps; CONTEXT.md:177 "process restart clears the registry"].

Every SSE frame uses `event: message` with no SSE `id:`, so `Last-Event-ID` resume doesn't exist (event.ts:12-19).

**Part model** (`Part` union, v1/session.ts:357-384): `text {text, synthetic?, ignored?, time?}`, `reasoning {text, time{start,end?}}`, `file {mime, filename?, url, source?}`, `tool {callID, tool, state, metadata?}`, `step-start {snapshot?}`, `step-finish {reason, snapshot?, cost, tokens{total?,input,output,reasoning,cache{read,write}}}`, `snapshot`, `patch {hash, files[]}`, `subtask {prompt, description, agent, model?, command?}`, `agent {name}`, `retry {attempt, error: APIError, time}`, `compaction {auto, overflow?, tail_start_id?}` (v1/session.ts:87-256). The assistant message carries `parentID` (the user message), `agent`, `mode`, `providerID/modelID`, `path{cwd,root}`, `cost`, `tokens`, `finish?`, and `error?` ∈ `ProviderAuthError | UnknownError | MessageOutputLengthError | MessageAbortedError | StructuredOutputError | ContextOverflowError | ContentFilterError | APIError` (v1/session.ts:385-395, 453-482).

**Streaming.** Text and reasoning stream as `message.part.delta` with `field:"text"` (oc:packages/opencode/src/session/processor.ts:294-306, 513-524). The full part is re-sent via `message.part.updated` at start and end. **Tool input does not stream in v1.** The part is created as `pending {input:{}, raw:""}` on `tool-input-start`, and input deltas are ignored (processor.ts:236-244, 315-329).

**Tool state machine:** `pending{input,raw}` → `running{input, title?, metadata?, time.start}` → `completed{input, output, title, metadata, time{start,end,compacted?}, attachments?}` | `error{input, error, metadata?, time}` (v1/session.ts:259-313). Tools can push interim `title`/`metadata` while running through `ctx.metadata(...)`, which re-emits `message.part.updated`. Bash uses this to stream an output preview in `metadata.output`, and its final metadata is `{output, exit, truncated, outputPath?}` (oc:packages/opencode/src/tool/shell.ts:475-530, 587-592).

**Steps/cost/diffs.** At `step-finish` the processor writes the `step-finish` part (tokens and cost), updates the assistant message, then computes a snapshot patch and emits a `patch {hash, files}` part if files changed (processor.ts:435-484). It also kicks off a summary that emits `session.diff`. `edit` and `write` put a unified `diff` (plus `filediff`) in tool metadata (oc:packages/opencode/src/tool/edit.ts:181-206, write.ts:58-61). `apply_patch` puts `files[{filePath, relativePath, type: add|update|delete|move, patch, additions, deletions, movePath?}]` there (oc:packages/opencode/src/tool/apply_patch.ts:62, 194-213). `GET /session/:id/diff?messageID=` returns `FileDiff[]`.

**Todos:** `todowrite` replaces the whole list. `todo.updated` carries the full list, and `GET /session/:id/todo` reads it.

## 4. Subagents

- **Spawn path.** The model calls `task {description, prompt, subagent_type, task_id?, command?, background?}` (task.ts:43-64). A user can also trigger it with `@agent` / `subtask` parts, which the prompt loop executes through the same `TaskTool` (prompt.ts:300-330). Flow: permission `task` with pattern `[subagent_type]` (task.ts:119-129) → create child session `{parentID, agent, title, permission: derived from parent + denies for todowrite/task unless allowed}` (task.ts:142-174) → `ctx.metadata({title, metadata:{parentSessionId, sessionId, model, background?}})` (task.ts:185-195) → `ops.prompt` on the child.
- **Live discovery.** (a) `session.created` with `info.parentID` on the same stream; (b) the parent's `tool` part (`tool:"task"`, `state.status:"running"`) whose `state.metadata.sessionId` gives the child ID. (b) arrives in the same tick and links the edge to the exact `callID`. Fallback: `GET /session/:id/children`.
- **Same stream.** The child is created via `sessions.create` in the parent's instance context, so its events carry the same `directory` (event-v2-bridge.ts:18-31). [Live multi-session observation not done → **needs verification**.]
- **Resume.** `task_id` reuses an existing child session (task.ts:136-138). Several `task` calls can therefore map to one child agent node.
- **Nesting.** `subagent_depth` (default 1) counts ancestors (task.ts:105-117, docs/config). Children also get `task: deny` unless their agent explicitly permits it (task.ts:150-152).
- **Completion back to parent.** Foreground: the tool result is `<task id="ses_…" state="completed"><task_result>…last text part…</task_result></task>`, or the tool errors with `Subagent failed (task_id: …)` (task.ts:66-79, 204-224, 328-356). Background (experimental): it returns `state="running"` right away. On finish, it **injects a synthetic user text** into the parent (`<task … state="completed|error"><summary>Background task completed: …`) and re-runs the parent loop (task.ts:228-256, 316-319). A running foreground task can be promoted to background via `POST /experimental/session/:id/background` (experimental.ts:159-172). No event is emitted for job state. Infer it from the child's `session.status` and the parent's tool part `metadata.background/jobId`.
- **Abort cascade.** Aborting the parent aborts foreground children (`ctx.abort` → `ops.cancel(child)`, task.ts:322-356). `SessionRunState.cancel` also cancels background jobs whose `parentSessionId`/`sessionId` match, transitively (oc:packages/opencode/src/session/run-state.ts:77-149).
- **Agents.** `mode ∈ primary | subagent | all` (oc:packages/opencode/src/agent/agent.ts:38). Built-ins: `build`, `plan` (primary); `general`, `explore` (subagent); `compaction`, `title`, `summary` (hidden primary) (agent.ts:141-256; live `/agent`). docs/agents also lists a `scout` subagent that isn't in the v1.18.33 source or the live `/agent` output (doc drift). The subagent model defaults to the invoking message's model unless the agent sets `model` (task.ts:181-184).

## 5. Status and liveness

- `session.status` is published on every `SessionStatus.set`. `idle` also publishes the deprecated `session.idle` and drops the entry from the map (oc:packages/opencode/src/session/status.ts:39-47). `GET /session/status` returns only non-idle sessions for **that directory's instance** (live: `{}`).
- Transitions: the runner's `onBusy` → `busy`, `onIdle` → `idle` (run-state.ts:58-66). Each loop iteration and LLM attempt re-sets `busy` (prompt.ts:1089; processor.ts:653). Provider retries set `retry{attempt, message, action?, next}`, where `next` is the epoch ms of the next attempt (processor.ts:674-686). A `retry` part is also written. **Rate-limit vs network is not distinguished** in the status. Classify from `action.reason`, the retry part's `error.statusCode`, or the message [unverified field contents].
- **Errors.** `session.error` is published and the assistant message gets `error`. A non-overflow error sets status `idle` from inside the processor (`halt`, processor.ts:610-640). `ContextOverflowError` with autocompaction triggers compaction, and the session stays busy (processor.ts:619-633). Compaction shows up as a `compaction` part, `session.time.compacting`, and `session.compacted`.
- **Parent idle while children run:** not with foreground tasks (the parent stays busy inside the tool call). **Yes** with background tasks, which is the exact "marked completed while still working" trap. Per the design notes, "background subagents and tasks do not make their parent Session active" (CONTEXT.md:177).
- **Background shells:** v1.18.33 has none built in (bash runs synchronously with a timeout). `POST /session/:id/shell` runs a user shell as a pseudo-turn and fails with BusyError if the session is running (run-state.ts:96-105). PTYs (`/pty`, `pty.*` events) are user terminals, not agent activity.
- **Heartbeat:** `server.heartbeat` every 10 s on both SSE routes. Treat the server as unresponsive after about 25 s without any frame.
- **Prompt while busy** (v1). The user message is persisted at once, and `ensureRunning` joins the active run (oc:packages/opencode/src/effect/runner.ts:115-139). The loop only exits when the latest assistant answers the latest user message (prompt.ts:1104-1125). A mid-run prompt therefore gets picked up at the next step boundary, i.e. implicit steering. The v2 API makes this explicit with `delivery: "steer" | "queue"` (oc:packages/schema/src/session-delivery.ts; CONTEXT.md:102-103).

## 6. Human-in-the-loop

- **Permissions** (v1). Tools call `ctx.ask({permission, patterns, always, metadata})`. Rules are evaluated per pattern: `deny` → tool error, all `allow` → proceed, otherwise `permission.asked` is published and the tool blocks (permission/index.ts:70-107). Replies: `once` resolves only this request. `always` adds `always` patterns to an **in-memory, per-instance** approved list and auto-resolves other pending requests in the same session that now pass. `reject` fails this request (`CorrectedError` with feedback if `message` is given) and **rejects all other pending requests for that session** (permission/index.ts:109-171). Routes: `GET /permission` and `POST /permission/:requestID/reply {reply, message?}`. The legacy `POST /session/:id/permissions/:permissionID {response}` still exists (handlers/session.ts:370-385).
- Permission keys seen in code: `bash`, `read`, `edit` (also covers write and apply_patch), `glob`, `grep`, `webfetch`, `websearch`, `task`, `todowrite`, `skill`, `lsp`, `question`, `plan_enter`, `plan_exit`, `external_directory`, `doom_loop` (same tool with the same input 3×; processor.ts:350-379), and MCP tool keys (session/tools.ts:408).
- Child-session requests carry the **child's** `sessionID`. ace must bubble them up to the thread. `tool{messageID, callID}` links each request to its tool part.
- **Questions:** `question` tool → `question.asked {id, sessionID, questions[{question, header, options[{label,description}], multiple?, custom?}], tool?}`. Reply with `POST /question/:id/reply {answers: string[][]}` (one array of labels per question), or reject with `POST /question/:id/reject`. A rejection fails the tool.
- **Plan/build switching.** `plan` is a primary agent with edits denied, except for plan files (agent.ts:156-180). Switch agents per message with `agent` in the prompt body. `plan_exit` (only with `OPENCODE_EXPERIMENTAL_PLAN_MODE` **and** `client==="cli"`) asks a `question` ("switch to the build agent?"). On "Yes" it appends a synthetic user message with `agent:"build"` (oc:packages/opencode/src/tool/plan.ts:15-78; registry.ts:248). This gives ace a "plan review" interaction for free, but only under those flags.

## 8. History import

`GET /experimental/session?roots=&directory=&search=&archived=&limit=&cursor=` lists across **all projects**, sorted by `time_updated`, with an `x-next-cursor` header (experimental.ts:138-157). `GET /session` is limited to the current project (`?directory`, `roots`, `search`, `start`, `limit`, `scope=project`; oc:packages/opencode/src/session/session.ts:546-553). Then use `GET /session/:id/message?limit=&before=` (`{info, parts}[]`), `GET /session/:id/children`, and `/todo`, `/diff`. Rebuild agent trees from `parentID`. `opencode export <id>` dumps JSON. The local DB currently holds 801 sessions, 240 of which have a parent (read-only count).

## 9. Extras

- **Attachments:** `file` parts with a `data:` or `file:` URL; `file:` paths are read server-side (prompt.ts:786-830). MCP resources become `file` attachments on tool results.
- **MCP:** `GET /mcp` (status), `POST /mcp`, connect/disconnect, OAuth routes. Event: `mcp.tools.changed`. Tool names are `sanitize(server) + "_" + sanitize(tool)` (oc:packages/opencode/src/mcp/catalog.ts:117-119). **They are indistinguishable from built-ins by name alone.** Match against `GET /mcp` server names, or diff `GET /experimental/tool/ids`.
- **LSP:** `GET /lsp`, `lsp.updated` (empty payload). The old `lsp.client.diagnostics` event is gone. Diagnostics appear in `edit`/`write` tool metadata (write.ts:94-95). The `lsp` tool is experimental.
- **Agents/skills/commands:** `GET /agent`, `/skill`, `/command`. Providers and models: `GET /provider`.

## 10. Gaps, risks, adapter notes

- **Dual runtimes.** Legacy sessions (`message`/`part` tables, `message.part.*` events) and core v2 (`session_message`, `session.next.*`) coexist. Whether a v1-driven session ever emits `session.next.*` is unclear: in the source, only `packages/core/src/session/runner` publishes them. **Pick one per thread** (v1 for now) and ignore the other family. Design the adapter around a normalized internal event stream so v2 can replace v1.
- **No replay on live streams.** After a reconnect, refetch `GET /session/status`, `/permission` and `/question` (per directory) plus the messages of active sessions. Use the `sync` envelope's per-aggregate `seq` to detect gaps.
- **In-memory HITL.** A server restart or instance dispose rejects pending requests. ace must mark them `expired` instead of leaving them open.
- **Cross-process blindness:** see §2. Sessions run by another OpenCode process only appear as DB changes (polled list / `time.updated`).
- **Fork lineage is lost** (no `forkedFrom`). Children are distinguishable from forks only by `parentID`.
- **Docs drift:** port default, `scout`, the permission body `{response, remember?}` in docs/server vs `{response}` in code, and docs links to the stale v1 `types.gen.ts`.

### Status derivation (per agent node = session)

`starting`: prompt sent, no `busy` yet. `working{activity}`: `busy`; activity comes from the newest `running` tool part, else streaming reasoning/text. `blocked{human}`: an unanswered `permission.asked`/`question.asked` for this session. `blocked{subagents}`: busy **and** a `running` `task` part whose child is busy. `blocked{background_task}`: idle with a background child (`metadata.background`) that is still busy. `blocked{rate_limit|network}`: `retry`, classified from the error. `interrupted`: last assistant `MessageAbortedError`. `failed`: other `error` / `session.error`. `idle`: `idle` with no busy descendants. `unresponsive`: busy with no frames for more than 25 s, or the SSE stream is dead. **A thread is done only when the whole subtree is idle and no interactions are pending.** Expect a background-injected re-activation of the root.
