## Conclusions for the canonical protocol

1. **ace derives all status itself.** No provider reports status for a subtree. Each adapter emits per-agent facts (turn boundaries, open interactions, live background tasks, retries), and the daemon folds them over the tree. "Done" for a thread means: every agent idle, no open interactions, no live background tasks, no queued input. The per-provider "true idle" rules are in each file's status section; Claude's is the most explicit (`session_state_changed: idle` + empty `background_tasks_changed`).

2. **Background work is its own entity.** Every provider has work that outlives a turn: background shells, monitors, background subagents, open exec calls. Model it as `BackgroundTask {id, agentId, kind: shell | monitor | subagent | other, status, startedAt, endedAt}` rather than a flag. That makes `blocked{on: background_task}` concrete and lets the UI list and stop tasks.

3. **Runs are not request/response.** Agents start turns without ace asking: task notifications, goal continuations, queue dispatch, background completions. A `Run` needs a `trigger: user | background_completion | subagent_result | goal | queue | schedule | unknown`, and adapters must accept turns they didn't request.

4. **Agent nodes carry a fidelity level.** `full` (live transcript), `summary` (only start/end and a result), or `placeholder` (only the spawning tool call, as with Antigravity). The UI then shows "transcript not available from this provider" instead of an empty pane.

5. **Adapters must tolerate out-of-order trees.** Codex can send child events before the spawn item and can fail to attach a child under load. The tree builder buffers events for unknown agent ids and resolves parentage by lookup (`thread/read`, `/session/:id/children`). It must never drop events for an unknown id.

6. **Interactions need more states.** `pending | resolved | cancelled | expired`, plus `blocking: boolean` for Codex's async questions. Pending requests die with the provider process for OpenCode, Claude (unless `defer`), Cursor and Antigravity, and Codex aborts them at turn end. They must become `expired`, never stay open forever. Resolution is first-answer-wins across devices, which matches Codex's own semantics.

7. **Steering is a capability, with an ace-side queue as fallback.** Native steer on Claude, Codex and OpenCode. Cursor and Antigravity cancel on re-prompt, so ace holds the queue and sends after the turn ends. The UI reads `capabilities.steer` to decide what the button does.

8. **Error classification is a shared module.** Cursor and Antigravity report errors and quota exhaustion as message text. One classifier with recorded fixtures per provider maps text to `failed | blocked{rate_limit} | blocked{network}` and keeps the raw text.

9. **The raw record is the whole provider item, not just name+input.** Codex and Cursor don't send the model's tool name for most calls. Store the full native item verbatim and infer the ace tool kind from its type and shape, with `custom` as the fallback. Tool failure is also inferred where providers don't send it (Cursor: `rawOutput.error`, `exitCode ≠ 0`, `rejected`).

10. **Liveness comes from ace.** Only OpenCode sends a real heartbeat. The daemon supervises every provider process (exit, stdio EOF) and runs per-agent silence timers to produce `unresponsive`.

11. **Process supervision differs per provider, so it belongs in the daemon core.** One multiplexed process (Codex, OpenCode), one per thread (Claude, Cursor), one heavy process per instance (Antigravity). The supervisor needs spawn, readiness, idle reaping with resume, crash restart, and a per-provider memory budget.

12. **Version churn is high everywhere,** with releases weekly or faster, and docs lag the code in every case. Per provider: generate types from the installed binary where possible (Codex `generate-ts`, OpenCode `/doc`, Claude `sdk.d.ts`, ACP JSON schema), decode leniently, gate features on capability probes rather than versions, and pin behaviour with recorded fixtures in CI.

## Auth and terms of service

**Decision (2026-10-02): ace drives the user's own locally installed CLIs, using whatever login the user set up in each one.** ace never offers provider login, never stores provider credentials, and is never hosted. Remote and mobile access means the user's own devices connecting to their own daemon. In practice:

- Spawn the binary found on the user's PATH, not a bundled copy. For Claude, point the SDK at the user's `claude` with `pathToClaudeCodeExecutable`; for Codex, run the user's `codex app-server`.
- Detect whether each CLI is installed, its version, and its auth status. If the user isn't logged in, show the CLI's own login command (`claude /login`, `codex login`, `agent login`, …) instead of an ace login flow.
- Because the installed version is whatever the user has, gate features on capability probes and generate schemas from the installed binary where possible (conclusion 12).
- Antigravity remains a special case: its ACP server is a separate download, not the `agy` CLI, and the ToS clause about third-party software still needs Google's position for `oauth-personal`.

The vendor positions that led to this decision:

| Provider    | What the vendor says                                                                                             | Safe default                                                                      |
| ----------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Claude      | Third parties may not offer claude.ai login or rate limits without approval (Agent SDK overview)                 | API key, or the user's own local CLI login behind explicit opt-in; ask Anthropic  |
| Codex       | App-server auth "has never been permitted for commercial or hosted services"; local/open-source use is tolerated | Local daemon using the user's own `codex login`; never hosted                     |
| Antigravity | Using third-party software with Antigravity OAuth is a breach of the ToS                                         | `gemini-api-key` / Vertex; get Google's position before enabling `oauth-personal` |
| Cursor      | Nothing found that restricts ACP clients; ACP is documented                                                      | User's own `agent login` or API key                                               |
| OpenCode    | Open source; users configure their own provider keys                                                             | User's own config                                                                 |

The common thread: ace running **locally**, driving the CLI the user installed and logged into, is the most defensible position. A hosted ace that holds users' subscription credentials is not.

## Next step: live fixture spike

The open questions that most affect the protocol, in priority order:

1. Claude: is `session_state_changed` emitted by default, and in what order relative to `result` and `task_notification`? Is `task_id` the same as `agentId`?
2. Codex: what a client sees when a background terminal exits after `turn/completed`; how often child attachment fails under parallel spawns.
3. OpenCode: child-session events interleaved on `/global/event` during a real `task` run; background-subagent re-wake sequence.
4. Cursor: which session id subagent approvals arrive on; whether background shell completions surface over ACP at all.
5. Antigravity: what `start_subagent` returns; how `/plan` approval reaches an ACP client; whether anything is pushed between prompts.

Answering these needs short real sessions on each provider, which spends the user's subscription quota. The proposal is a small recorder in the new repo that runs a fixed set of scripted prompts per provider (single tool call, approval, question, foreground subagent, background subagent, background shell, interrupt mid-tool) and saves the raw frames as fixtures. Those fixtures become the adapters' contract tests.
