# First-message recovery

Socket `thread.create` and `thread.prepare` in worktree mode prepare the physical worktree before committing a thread, command receipt or delivery intent. A preparation failure returns `commandResult` with `ok: false` and the existing `workspace_unavailable` error code, except for a requested `base` that can't be used: `worktree_base_not_found` (no such local branch, or the remote answered without it) and `worktree_base_unreachable` (the remote couldn't be reached within the fetch timeout, 15 s by default, and the branch was never fetched before). Those results also carry `code`, `title` and `detail`. The client retains its draft and can retry after fixing the repository or base branch. Preparation errors do not create an empty failed thread or an accepted receipt. Admission checks provider selection, account conflicts, permission and launch options, input budgets and capacity before Git runs. An engine slot and command-specific owner span preparation and acceptance. Concurrent commands for the same thread return `thread_creation_in_progress`; completed receipts skip preparation. Acceptance revalidates the owner, canonical project and requested base selection (`base` when sent, else `baseBranch`, else `HEAD`).

A remote `base` is fetched just before the worktree is made: only that branch, into its remote-tracking ref, with no tags, prompts, `FETCH_HEAD` or maintenance, outside the repository's mutation lease so a fetch killed by its deadline never quarantines the repository. When the fetch fails but the remote-tracking ref exists, the worktree starts from that cached copy and `details.base.fetch` is `unreachable`. The worktree's own `ace/` branch starts at the resolved commit with no upstream, so its first push sets a same-named upstream. The person's checkout, index, HEAD and local branches are never touched. Late preparation (a worktree thread accepted without a prepared workspace) never fetches: it starts from the recorded `details.base.head`, else the recorded `baseBranch` as Git resolves it. The prepared root and branch enter thread metadata and the engine session binding in the acceptance transaction.

A bounded SQLite journal records ownership before physical work begins and pins the base commit. Disconnects and admission rejection release the slot and clean the exact uncommitted worktree and unchanged branch. Startup recovers orphaned preparation in the background; new preparation waits for recovery. Accepted resources remain with their thread. Creation and agent handoffs share the cleanup checks, including preservation of external edits or commits and compare-and-delete for branches. At most 16 uncommitted creation resources can remain, including failed safe cleanup across restarts. A collision or uncertain partial operation preserves the user's resources and requires cleanup before more preparation can proceed.

Internal admissions, previously prepared threads, restarts, provider session opening, and checkpoint preparation can still fail after acceptance. A typed `DeliveryNotStarted` failure retains the original command input and context as a queued user message, pauses its queue for manual recovery, and records the error notice. The thread stays waiting on its queue. `queue.get` exposes the retained input after reconnect or restart; the user can `queue.edit` and `queue.resume`, or remove it and resend.

Failures whose consumption is unknown retain the existing uncertain-message behavior. They require review and explicit removal/resending rather than automatic replay. An acknowledged message never becomes runnable again because a later transport operation failed.

`fs.home` now returns both `path`, the configured home for display, and `canonicalPath`, its realpath. Clients should compare canonical project roots with `canonicalPath`. The fake daemon follows the same rule when its seeded home has a display alias.
