# Performance audit, 9 October 2026

This audit follows the hot paths across the web client, workers, daemon, persistence, provider adapters, relay and device viewer. It is a source review plus targeted regressions and production bundle measurements. It is not a timing profile of every feature. The delivery PR records the combined full-check, merge and installation status separately.

All bundle gates passed with their existing budgets after cross-device PR integration. Client-worker headroom is 1.02 KiB. The combined machine worker is 71.85 KiB, also within its unchanged 73 KiB limit.

Further defects now have regressions that fail with the previous behavior and pass with the fixes:

- The transcript selector saved six fixed cache inputs but compared seven. A fixture with 5,000 settled messages and ten unchanged notifications performed 400,000 item reads. Saving the complete fixed input list reduces that to zero. Interaction versioning also invalidates a replaced question when its count stays the same. Explicit ancestry dependencies handle child links arriving after a settled result without regrouping on ordinary streamed text. See [block-reader.ts](../apps/web/src/features/thread/transcript/block-reader.ts).
- The closed diff cache counted visible rows, although folds retain all hidden text. A 5,000-line unchanged file counted as one row and stayed cached beyond its memory allowance. The main and IndexedDB caches now share estimated byte accounting for visible and folded text. Open views retain their working set; after closing, the main cache has a 16 MiB bound. See [diff-service.ts](../apps/web/src/lib/diffs/diff-service.ts) and [diff-weight.ts](../packages/ui-core/src/diff-weight.ts).

- Fenced code previously ran a synchronous regex tokenizer during the first render while its worker job was pending. It now renders one plain text span immediately and applies colors after the worker responds. A regression checks readable source, exact whitespace and the single-span pending state. This removes main-thread fallback tokenization, but settled large fences still need line virtualization.

- Image loading admitted every distinct cold request immediately. Socket queue pressure and decoder contention across connections left thumbnails unavailable without retry. A per-connection scheduler now retains at most 64 pending metadata jobs, admits two reads within a 32 MiB reserved byte budget, shares scoped requests, and retries typed busy failures at most four attempts. Consumer leases remove obsolete queued work and stop client ranged reads when the last viewer unmounts. Already-running daemon thumbnail work can still finish because context RPC has no cancellation message. Client identity also fences displayed URLs when switching devices. The completed blob cache remains bounded at 48 MiB; that limit does not include mounted decoded images. Public regressions cover galleries, shared connections, cancellation through the real worker bridge, retry exhaustion and device switching. See [attachment-loads.ts](../apps/web/src/components/attachment-loads.ts).

The explicit full-array copy before creating an image Blob was removed for ordinary owned ArrayBuffers. Blob creation still snapshots its bytes, and alternate clients returning shared buffers retain a copy fallback. Original images still use sequential 64 KiB base64 requests: a 32 MiB original requires 512 requests and about 42.67 MiB of base64 payload before JSON framing. These are source-derived transfer costs, not latency measurements. Normal transcript attachments without thumbnails render as file chips rather than automatically downloading full originals.

File and browser channels now reuse the canonical client's validated responses instead of decoding each response again inside the worker. Malformed replies still fail at the external protocol boundary, and channel identifiers still require integers. The bundle reduction from this particular change was only 0.02 KiB; its purpose is removing repeated parsing and allocations during transfers.

Workers now instantiate the shared ClientCore without the page's project, history, authentication and file convenience methods. The public Client subclasses that same core and retains its convenience APIs. The split saved about 2.08 KiB per complete worker closure before admission checks. Structured-cloned tab arguments now have a bounded graph preflight before parsing: cycles, excessive depth and exponential expansion are rejected, while ordinary shared references remain valid. Removing reference-cycle memoization from private JSON workers therefore does not expose their recursive parsers to unbounded port graphs.

The native iOS transport probe from this task produced its first frame in 2,042 ms and 15 frames over 2,915 ms at a requested 5 FPS. That was a transport correctness probe, not evidence of smooth 60 FPS motion.

## Worker and GPU placement

Grammar parsing already runs in a dedicated CPU worker. The fenced-code pending preview now avoids its former synchronous fallback tokenizer. The main-thread costs left are source hashing, worker message cloning, React updates and token DOM/layout. Scheduling and line virtualization should be addressed before adding more workers. A worker removes parsing from the UI thread but does not make an unbounded queue or an oversized result cheap.

GPU work is a better candidate for video decoding, compositing and drawing very large text views. The app already has experimental WebGPU/WebGL2 diff text rendering and a WebGL terminal renderer. Leave experimental diff rendering opt-in until it improves measured interaction latency and preserves accessibility, selection and copy. There is no measured justification here for implementing regex grammar parsing on the GPU.

Avoid one worker per small task. Keep specialized long-lived workers, explicit queue/byte limits and newest-request scheduling where old results are disposable. Stream only appended text or changed ranges. Move binary buffers with transferable ownership when the protocol permits it, rather than converting images/files to base64 JSON.

## Existing protections to preserve

Frame-batched client notifications, append-only streamed text, transcript windows, source-line virtualization, bounded highlighting caches, bounded actor batches, yielded history publication, disk-backed records, transport pressure limits and binary relay backpressure already reduce substantial load. Relay forwarding passes ciphertext buffers without another serialization step and pauses at its high-water mark. Adding another application compression or base64 layer would increase work there.

Follow-up performance tests should report p50/p95/p99 input delay, longest UI task, work per stream delta, retained memory after collection, worker queue bytes and device frame age. Run qualified timing checks on an idle host. A bundle-size improvement or a source-code finding is not a measured runtime speedup.

## Static scan scope

A full React Doctor scan covered 1,249 web source files and reported 326 diagnostics: 14 bug errors, 64 bug warnings, 72 performance errors, 42 performance warnings, 102 maintainability warnings, 28 accessibility warnings and four security warnings. These are candidates for investigation, not 326 confirmed defects. For example, its missing-origin warning on private dedicated-worker message handlers is not a window-message trust boundary. Compiler bailouts and lifecycle cleanup findings should be checked against the actual subscriptions and event handlers in small reviewed batches. The combined changed-code scan remained at 77/100 with only the two existing complexity warnings. The final ClientCore split changes worker entry points rather than React components.
